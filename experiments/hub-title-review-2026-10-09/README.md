# Comparing parent context across two Hub feeds

This review compares the saved feeds in `example-feeds` against the actual
October 9 harvest in `outputs/2026-10-09_arcgis_primary.csv` and
`outputs/2026-10-09_arcgis_distributions.csv`. It was produced on
`mngeo-harvest-tests`. No source configuration, production output, upload workflow,
or metadata schema was changed. Baltimore's experimental policy was enabled only
inside the comparison script's memory.

## Start with these files

- **mngeo_nonparcel_title_comparison.csv** contains every explicit non-parcel
  parent family in the saved MnGeo feed: **220 families and 1,638 records**.
  It includes each parent and its layers, so you can review complete families
  rather than isolated examples. Any family with `parcel` in a member's title
  was excluded from this review. This is comprehensive for that selection, not
  a complete list of all standalone MnGeo datasets.
- **baltimore_county_title_comparison.csv** contains all **224 records** in the
  saved Baltimore County feed, including three records excluded by our filters.
  This is Baltimore County, not the separate Open Baltimore city portal.

Both are UTF-8 CSVs. The filenames describe their source and review purpose;
the enclosing directory dates the comparison against the October 9 harvest.
The current and updated titles sit next to each other in the first two columns.

## What the columns mean

- `current_title`: the title actually present in the October 9 primary table,
  matched by stable ID across all sources. Blank means the record is absent from
  that harvest. It is not a simulated old title. `current_source_code` and
  `currently_harvested_via_this_source` show whether an existing record came
  through MnGeo/Baltimore County or another portal.
- `updated_title`: what the existing experimental harvesting code generates
  from the saved feed. Blank means the record remains excluded by the filter.
- `feed_title`: the source's original title, before our place suffix or context.
- `parent_title_from_feed`: an explicit same-item parent title, when available.
- `role`: parent, sublayer, or standalone item. A sublayer can have no explicit
  parent in the feed; a blank parent title or `parent_ID` makes that visible.
- `change`: changed, unchanged, newly included relative to the actual harvest,
  or still excluded. Newly included does not automatically mean newly created
  by the policy; saved-feed and current-harvest contents can differ.
- `ID`, `arcgis_item_ID`, `sublayer_number`, `parent_ID`: stable identifiers and
  the explicit parent relationship. IDs are never manufactured from titles.
- `current_harvest_links`: links actually found in the October 9 distributions
  table for this ID. `updated_links`: links generated by the experimental code.
  Each cell can contain multiple newline-separated URLs.
- `service_container_name_from_URL`, `service_root_URL`, and
  `items_sharing_service_container`: technical service organization, kept
  separate from the catalog's parent/child relationship.
- `illustrative_service_suffix_NOT_current_policy`: a discussion-only title
  made from a Baltimore service URL label. It is **not** the updated title and
  is **not** an implemented naming rule. It omits our geographic suffix to keep
  this illustration readable.
- `review_notes`: specific caveats. Different parent/layer year sets are flagged
  for review; this is a wording comparison, not proof that the dates are wrong.
- The final columns identify the input files for provenance.

## MnGeo: a parent often supplies useful catalog context

MnGeo provides explicit parent records and layer records sharing the same
ArcGIS item ID. The experimental rule verifies their service-root/layer URLs,
keeps the parent and layers, and appends the parent's title where it is not
already present. It does not infer a parent from similar descriptions or titles.

Examples:

| Actual current title | Updated title |
| --- | --- |
| Temp Yr30 Ln1 [Minnesota] | Temp Yr30 Ln1 - MN Temperature Average (1961-1990) [Minnesota] |
| Census ACS Block Group [Minnesota] | Census ACS Block Group - American Community Survey (ACS) [Minnesota] |
| Sensitive Lakeshore Sensitivity Index [Minnesota] | Sensitive Lakeshore Sensitivity Index - Sensitive Lakeshore Assessment [Minnesota] |

Within this non-parcel review, **1,374 current titles change**, **43 stay the
same**, and **221 records are absent from the current harvest**. Those 221 are
220 explicit parents plus one layer present in the saved feed. Two elevation
layers are already harvested through Hennepin County (`05b-27053`), rather than
MnGeo. Their real current titles are included, and their current source is noted.

For all MnGeo datasets, including parcels, the actual current harvest contains
**2,165 dataset records**. The updated saved-feed output contains **2,435**.
The difference consists of **234 admitted parent records** plus **36 otherwise
eligible saved-feed layers absent from the MnGeo source harvest**. Of those 36,
**35 already appear elsewhere in the actual harvest through other portals**;
only one is absent across all sources. Thus the proposed saved-feed output has
235 IDs absent from the entire current harvest: 234 parents and one layer.
Those 36 should not be credited to the parent policy. All current MnGeo dataset IDs are present
in the updated saved-feed output. Administrative `harvest_...` website records
are excluded from these counts, including those with blank Resource Class.

For records already supplied by another portal, `updated_title` means what the
MnGeo metadata would produce for that ID. It does not promise that a full
multi-source harvest would choose MnGeo over the other portal: the existing
shared ID deduplication and source ordering remain unchanged.

The rule can also produce repetitive or lengthy titles when a child already
contains much of the parent's wording. It avoids an exact repeated parent name,
but it does not attempt semantic rewriting. Filter the comparison by `change`
and read families together before deciding whether the naming is useful.

## Baltimore County: service organization is different

The Baltimore County feed has **224 different ArcGIS item IDs**, with **no
explicit parent/sublayer families sharing an item ID**. Many individual items
still identify a numbered service layer. Several items can point into the same
MapServer while remaining separate catalog items.

For example, these all belong to the service container named `Transportation`:
Tree Inventory, Railroads, Decorative Street Lights, Grass Mowing Routes,
Street Sweeping Routes, and Transportation Inspection Districts. In total,
16 items in this feed use that container. Tree Inventory's item ID is
`b459f3d0fcac4c6abaadbad6a6c92387`; Transportation Inspection Districts uses
`1c287fb6f804418d8543959785215886`. They are different items, not children of a
shared item represented by an explicit parent record.

Our same rules therefore produce:

> Tree Inventory [Maryland--Baltimore County]

The illustrative URL-based alternative would be:

> Tree Inventory - Transportation

That alternative could make a reader wonder why trees are classified as
transportation. The service name tells us how the publisher organized its server;
it does not establish that Transportation is a meaningful parent dataset title.
The feed does not explain the organizational reason, so we should not invent one.

Across Baltimore County, **221 currently harvested records retain exactly the
same titles**. The other three feed records are still excluded and have blank
current and updated titles. There are **29 service containers shared by multiple
item IDs**, but no parent suffixes are added from those container names.

## What this means for applying the rule more broadly

The explicit-parent rule appears useful when the catalog itself supplies parent
metadata, as MnGeo does. Applying exactly that rule to this Baltimore feed does
not change its titles. A rule that instead appends names extracted from shared
service URLs would be a different policy and could lower title quality.

These two feeds do not establish that every Hub would benefit from a universal
policy. Review additional sources and the long or repetitive MnGeo titles before
enabling it more broadly. Keep service containers separate from explicit catalog
parents; preserving server relationships does not require putting them in titles.

## Verification and limitations

The analysis checks unique IDs/identifiers, stable updated results when the feed
order is reversed, distribution-to-primary relationships, at least 50 non-parcel
families, and full Baltimore feed coverage. The CSVs are checked cell-for-cell
against the analysis intermediates, and current titles and links are checked
against the actual October 9 tables. No live API calls or link availability
checks were made. Feed timing/content differences are reported separately.

The existing MnGeo policy is used without editing the harvesting pipeline.
`scripts/compare_hub_titles.py` can regenerate analysis intermediates from the
input files. `support/` holds those intermediates and internal review previews;
use the two top-level CSVs for discussion.
